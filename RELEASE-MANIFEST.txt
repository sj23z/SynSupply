====================================================
PART 1 — SHARED REPORTING ARCHITECTURE
====================================================

app/Services/CustomerStatementService.php (NEW)
  The single source of truth for a customer's full transaction
  statement (invoices with line items, sales returns with returned
  items, payments split into payment/settlement/discount) and for
  aggregating totals across a set of customers. This is the exact
  same detail-level logic that previously lived only inside
  CustomerStatementController, extracted so the Area and Sales
  Representative reports can show a REAL hierarchical statement per
  customer instead of the single aggregate row they showed before —
  one implementation, reused everywhere, not four separate ones.

resources/js/Components/CustomerStatementTable.vue (NEW)
  The on-screen equivalent: one shared Vue component rendering a
  customer's statement table with the red/blue/green/neutral color
  coding, used by the Customer Statement page and, per customer,
  inside the Area and Sales Representative report pages.

resources/views/pdf/partials/customer-statement.blade.php (NEW)
  The PDF equivalent, @include'd by the standalone Customer Statement
  PDF and, per customer, by the Area and Sales Representative PDFs.

====================================================
PART 2 — HIERARCHICAL AREA / SALES REPRESENTATIVE REPORTS
====================================================

Both reports now genuinely show:
  Entity -> every customer under it -> that customer's full statement
  (every invoice with its line items, every payment/settlement/
  discount, every return with its returned products) -> aggregate
  totals (gross sales, returns, net sales, cash, bank transfer, other,
  settlement, discount, actual cash received, outstanding balance).

This is true both on-screen (AreaDetail.vue / SalesRepresentativeDetail.vue,
each customer collapsible, "Expand All"/"Collapse All" controls) and
in the PDF (report-area.blade.php / report-sales-representative.blade.php),
using the exact same CustomerStatementService output in both places.

====================================================
PART 3 — PRODUCT REPORT EXTENDED
====================================================

Every transaction row now includes: customer's area, customer's sales
representative, discount, returned quantity (via SalesReturnItem's
existing invoice_item_id link — no new schema), and the linked
invoice's payment status ("where the existing data model permits it" —
payments aren't linked to a specific line item, only optionally to an
invoice as a whole, so this is the honest equivalent rather than a
fabricated line-level payment link). Owner-only cost/COGS/profit
fields remain exactly as gated before this release — re-verified, not
assumed.

ADDENDUM — CUSTOMER GENERAL REPORT + PRODUCT FINANCIAL MOVEMENTS
====================================================

Same v1.0.4 release, updated after initial packaging per a final
correction (still v1.0.4, per explicit instruction not to create
v1.0.5).

A) CUSTOMER GENERAL REPORT — NOW HIERARCHICAL

Reports -> Customers previously showed one aggregate row per customer
(gross sales / returns / net sales / payments / balance) with only a
"View Statement" link to see detail on a separate page. It now shows,
directly on the same page: every customer with activity, each
expandable in place (Expand All / Collapse All controls) to reveal
their FULL statement — every invoice with its line items, every
payment/settlement/discount row, every return with its returned
products — using the exact same CustomerStatementTable component and
CustomerStatementService data already proven on the Customer, Area,
and Sales Representative reports. A "كشف مستقل" (standalone statement)
link remains as a convenience, but is no longer the only way to see
the detail. A new PDF (report-customers.blade.php, reusing the same
shared partial as the Area/Sales-Rep PDFs) supports the same complete
structure — not a summary-only document.

B) PRODUCT REPORT — FINANCIAL MOVEMENTS VIA Payment.invoice_id

Each product transaction row can now be expanded ("الحركات المالية")
to reveal every payment actually linked to that transaction's invoice
via the existing, unmodified Payment.invoice_id relationship — shown
as separate rows, never collapsed into one "Paid" figure, since one
invoice can have multiple payment rows (e.g. a cash payment, a later
bank transfer, and a discount adjustment). The same expansion also
shows full return detail (return number, date, quantity, value) for
that specific line item, sourced from the existing
SalesReturnItem.invoice_item_id link. No new financial relationship
was invented — both links already existed in the schema. The Product
PDF gained the same nested financial-movements detail per transaction.

One small, additive model change was required: SalesReturnItem had no
salesReturn() relation (confirmed by direct inspection before adding
it) — needed to eager-load return metadata (return_number, return_date,
status) for the new return-detail method. This is a new relation
method only; no existing behavior, column, or query changed.
